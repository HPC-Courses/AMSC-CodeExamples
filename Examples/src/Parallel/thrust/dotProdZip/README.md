# Dot products with Thrust zip iterators

This folder demonstrates how to compute pairwise dot products of 3D vectors
using Thrust. The same source can run on an NVIDIA GPU through the CUDA backend
or on the CPU through Thrust's sequential C++ backend.

## Files

- `dot_products_with_zip.cu`: example program, including random input generation,
  the dot-product functor, and two equivalent uses of zip iterators.
- `Makefile`: selects the CPU or GPU backend and builds the executable.
- `Makefile~`: backup copy of the Makefile; it is not used by `make`.
- `dot_products_with_zip`: executable generated by the build.

## How the example works

The program currently generates two sets of **1,000,000 3D vectors**. It computes
one scalar result per pair:

```text
result[i] = A0[i] * B0[i] + A1[i] * B1[i] + A2[i] * B2[i]
```

This is a collection of independent 3D dot products, not a reduction of two
million-element arrays to a single scalar.

Each set stores its x, y, and z components in three separate arrays, a layout
called *structure of arrays*. A `thrust::zip_iterator` presents matching
components as a tuple without constructing an additional array of 3D vectors.
The `DotProduct` functor reads those tuples and returns their dot product.
Its `__host__ __device__` annotations allow it to be compiled for either CPU or
GPU execution.

Random values are generated on the host in the range `[0, 1)`, using distinct,
fixed seeds starting at 1234 for the six component arrays. The arrays and the
results use `thrust::device_vector`; the selected Thrust backend determines
whether these containers use GPU or CPU storage.

The source demonstrates two forms of the same calculation:

1. Declare iterator types and named zip iterators, then call `thrust::transform`.
2. Construct the zip iterators directly in the `thrust::transform` call.

Both calls execute, and the second overwrites the first call's results. The
program prints the first four vector pairs and their dot products. To change
the problem size, edit `const size_t N` in `main()` and rebuild; there is no
command-line size argument.

## Requirements

- GNU Make.
- A C++20 compiler, such as `g++`, for the CPU build.
- CUDA Toolkit headers, including compatible Thrust and libcu++ headers, for
  both builds. The source uses `cuda::std::tuple` and Thrust zip-iterator APIs.
- `nvcc` for the GPU build, plus a compatible NVIDIA GPU and driver to run it.

The Makefile searches `/usr/local/cuda/include` and
`/usr/local/cuda/include/cccl` by default. CPU execution does not require a GPU.

## Build and run

Run these commands from this folder.

For the GPU:

```bash
make BACKEND=gpu
./dot_products_with_zip
```

GPU is the default, so plain `make` selects the same backend. The default GPU
architecture is `sm_89`; select the architecture appropriate to your GPU when
needed, for example:

```bash
make BACKEND=gpu CUDA_ARCH=sm_86
```

For the CPU:

```bash
make BACKEND=cpu
./dot_products_with_zip
```

The CPU build uses `THRUST_DEVICE_SYSTEM_CPP`, which runs sequentially; it does
not enable OpenMP or other multicore parallelism. The GPU build explicitly
selects `THRUST_DEVICE_SYSTEM_CUDA`.

Both builds produce the same executable name. Each invocation rebuilds it, so
switching backends requires no intermediate cleanup.

Override the toolkit path or CPU compiler if needed:

```bash
make BACKEND=gpu CUDA_HOME=/usr/local/cuda-13.4
make BACKEND=cpu CXX=g++ CUDA_HOME=/usr/local/cuda-13.4
```

The Makefile also accepts `NVCC`, `CXXFLAGS`, `CPPFLAGS`, `LDFLAGS`, and `LDLIBS`
for build customization. Default compiler flags are `-O3 -std=c++20`.

Remove the generated executable with:

```bash
make clean
```

## Interpreting timings

To measure the complete program for each backend:

```bash
make BACKEND=cpu
time ./dot_products_with_zip
make BACKEND=gpu
time ./dot_products_with_zip
```

Shell `time` reports elapsed wall time (`real`), CPU time in user code (`user`),
and CPU time in the operating system (`sys`). These CPU-time fields do not
measure GPU kernel execution time.

Total runtime includes random input generation, allocations, both transform
calls, printing, and cleanup. The GPU version also includes CUDA initialization
and host/device transfers. Even with one million vector pairs, each dot product
requires only three multiplications and two additions, so total runtime alone
does not isolate the speed of the calculation.

For computation-only benchmarking, add a warm-up and measure repeated transform
calls separately from setup and output. Use CUDA events on the execution stream
and wait for the stop event before reading GPU elapsed time. The current example
contains no internal benchmark or automated correctness comparison.
